AM243x Boot Memory Map

Memory map — AM243x secure boot

The full boot chain on an AM243x LaunchPad (HS-FS): ROM FBL → SBL on Cortex-R5F → verified application, with the Cortex-M4F enclave in the path only in config A. Each band is one reserved segment inside the available memory, filled in proportion to how much is used. Figures come from the linker .map files and from on-target measurements.

Conventions and caveats

  • Band height is proportional to the reserved size, with a 34 px floor so the label fits — small regions (the public key, the IPC mailboxes) therefore look larger than they are. The horizontal fill shows used / reserved and is always drawn to true scale.
  • Sizes are KiB of 1024 bytes, which keeps every reserved region round, since all of them are powers of two. Anything under 1 KiB stays in bytes — an 8-byte high-water mark says more that way than as 0.01 KiB. Key and signature lengths stay in bytes throughout, because that is how FIPS 204 states them.
  • Stack figures are on-target high-water marks from stack painting (STACK_PAINT=1), not static estimates. Both configurations are measured. The heap is the one exception: there is no heap painting, so .sysmem counts as fully used.
  • The 128 KiB .stack reservation is sized for config B, where PQClean's ML-DSA runs on this core: its frame is dominated by fixed-size arrays (polyvecl mat[K] alone is 8×7 polynomials of 1 KiB) and peaks at 92,856 B. Config A needs 1,432 B. One size is kept for both, because an identical memory map is what makes them comparable.
  • Config B never loads the enclave. It skips the multicore ELF entirely, so the M4F is never started, the enclave image need not be flashed, and the bootloader's 56 KiB gElfBuffer disappears from .bss — which is why B carries ~20 KiB more ROM but ~58 KiB less RAM than A.
  • Only config B links malloc: PQClean's fips202.c allocates SHAKE contexts (208 B each, a handful live at a time). Config A emits no .sysmem section at all.
  • The ROM figures include the root-of-trust step: before the public key is used for anything, the SBL hashes it with SHA-256 and compares the result against a device fuse reference. It runs through the same implementation on the same core that configuration uses for the image — so in config A it is a second IPC round trip. The comparison is advisory on this HS-FS part, whose key-hash fuses are not programmed.
  • The flashed SBL is larger than its own code by a constant: tiimage − ROM = 231,997 B exactly in both configurations, which is SYSFW, the board configuration and the certificates that rom_image_gen.py prepends.
  • Flash is 64 MiB of OSPI NOR, and nothing executes from it — XIP reads return corrupted data under this board's OSPI configuration, so everything is copied into MSRAM first. The application ceiling is therefore a RAM limit, not a flash one.
  • The APPIMAGE region reads back empty in both configurations. It binds TI's encrypted-boot scratch buffer, and this project does not define ENC_BOOT, so nothing references it and the linker drops it.
  • The R5F's 64 KiB of tightly-coupled memory (ATCM + BTCM) is completely unused — the SBL runs entirely from MSRAM.
